# Conformance corpus — provenance

Every file in `fixtures/` is **generated by this repository**. Nothing here was
downloaded, and nothing here is third-party content.

| Property | Value |
|---|---|
| Source | `core/burrow-engines/testsupport/minimal_pdf.rs` |
| Generator | `cargo run -p burrow-engines --example make-conformance-fixtures` |
| Licence | `MIT OR Apache-2.0`, the same as the rest of the repository |
| Redistributable | Yes, without restriction |
| Contains third-party content | No |
| Contains personal or sensitive data | No |

That is a deliberate choice, and it is why this directory exists at all rather than the
fixtures living in `corpus/`. `corpus/files/` is gitignored precisely because corpora are
large and often not ours to redistribute (see `corpus/manifest.toml`). A committed
fixture has to answer for its licence, its source, and whether we may ship it; generated
output answers all three by construction.

The cost is that these files exercise what *we* can build, not what the wild contains.
Real-world adversarial documents belong in `corpus/`, fetched and checksummed, and are
what the regression runs on the self-hosted machine are for. This directory is the
conformance floor, not the ceiling.

## Why this is not inside a crate

`expectations.json` is the contract between **two** implementations of
`DocumentEngine`: the native PDFium one in `core/burrow-engines`, and the web one that
M1 PR 4 will build over a JS bridge (ROADMAP M1 item 12). Both read this file and must
produce identical typed outcomes. Putting it inside either crate's `tests/` would make
one of them reach into the other's test directory for shared data, and would invite the
two sides to keep separate lists that silently drift.

## The files

`expectations.json` records the outcome for **each engine separately** — `page_count` is PDFium,
`structure_check` is qpdf — because several of these files exist precisely because the two
disagree. See [ADR 0016](../../docs/adr/0016-differential-conformance.md).

### The three hidden bombs

Each is a one-line edit to `xref-bomb.pdf`'s declaration, and each was a **working bypass** of
the pre-scan found by security review of M1 PR 3 — each made the scan read *nothing*, and a scan
that found no cross-reference treated "nothing declared" as "nothing to declare". They were
reproduced inside one native test until M1 PR 4b moved them here, because the web path runs the
same pre-scan and had never been shown to reject them.

### `truncated-mid-object.pdf` and `trailer-removed.pdf`

The two files **qpdf reads and PDFium refuses** — ADR 0013's *The repair question, answered*.
They are the evidence for keeping qpdf at all, and the reason `expectations.json` records an
outcome per engine rather than one per file.

### The canary, and why there are two of them

`canary.pdf` carries a **fixed** canary, `BURROW-CANARY-FIXED-0000`. The leak tests —
`core/burrow-engines/tests/secret_leak.rs` and `apps/web/e2e/console-silence.spec.ts` — generate
a **fresh** canary per run instead, and do not use this file.

That is not duplication. A leak matcher needs a string nothing else could have produced, or a
stale match reads as a fresh leak. A corpus fixture is pinned by sha256 and cannot have one. The
two do different jobs: this file asks whether both implementations reach the same typed outcome
on a file built to make a parser quote it, and that answer must not depend on a random string.

### `xref-bomb.pdf` — the one exception to everything above

330 KB, structurally valid, and declares a cross-reference stream of twenty million
entries: 340 MB uncompressed, which deflates to a few hundred kilobytes and which PDFium
must inflate to parse the file at all. It ends up resident in about 1.2 GB.

It is the regression test for a real gap. The size-based memory pre-check predicts ~16 MB
for it — that check is a function of the input's *length*, and a declared size is not in
the length — so before the measured post-open check existed, this returned `Ok` with one
page and a gigabyte held for the lifetime of the handle.

Two ways it breaks the rules on this page, both deliberate:

- **Generated by Python, not by the Rust example.** `tools/make-xref-bomb.py`, committed
  beside it. The file needs a real deflate compressor to get its expansion ratio, and a
  hand-rolled encoder in the Rust test support would produce something several times larger
  for no benefit. Python ships `zlib`; the generator is fifteen lines and deterministic, so
  the digest below is stable.
- **It used not to be listed in `expectations.json`**, because its outcome depends on the
  `Limits` it is opened with and schema 1 could not say so. Schema 2 records limits per case,
  so it is in the corpus now. `core/burrow-engines/tests/limits.rs` still drives it at full
  scale separately — that test really does allocate ~1.2 GB, which the conformance run
  deliberately does not.

Regenerate with:

```bash
python3 tools/make-xref-bomb.py tests/conformance/fixtures/xref-bomb.pdf
```

Digests are recorded in `expectations.json`, not here: one place, checked on every run.

### `objstm-bomb.pdf` — the bomb the pre-scan does *not* see

The other Python-generated fixture, and the one that documents an open defect.

Its catalogue, page tree and page all live inside a **compressed object stream** padded with
spaces, so PDFium must inflate 200 MiB to find the catalogue. Every number the pre-scan reads is
modest and honest: the cross-reference declares `/Size 6`, and the big stream's `/Length` is its
real compressed length.

Measured on a 1.4 MB variant against the default 1 GiB ceiling: the pre-scan passes it
(estimating 384 bytes), PDFium peaks at **2,437 MB**, and the file returns **`Ok`**. Neither
check fires — the measured post-open check compares the resident set before and after, so a peak
that occurs *during* is invisible to it.

The committed fixture is smaller on purpose. 200 MiB is pinned from three directions: above the
96 MiB conformance ceiling plus the 64 MiB noise margin, above `MIN_CONVERGING_MEMORY_BYTES` so
the case is not exercising recycling thrash instead, and **below qpdf's 256 MiB
`flate_max_memory`** (ADR 0013 §5) — past which qpdf refuses the file and the case stops
isolating the gap. That last constraint is the finding in miniature: qpdf has a decompression
ceiling and honours it; PDFium has none configured.

It is in the corpus with `known_gap` pointing at
[#24](https://github.com/TensorGreed/burrow/issues/24). Its recorded outcome is what burrow
**does**, not what it should do, so fixing the pre-scan will break the expectation and force the
fixture and the issue to be closed together.

```bash
python3 tools/make-objstm-bomb.py tests/conformance/fixtures/objstm-bomb.pdf
```

## `known_gap` has a ceiling, and every entry has a deadline

A `known_gap` is green CI and an open defect at the same time. That is the right trade against
the alternative — a skipped test records *"untested"*, which is the wrong memory to leave for
M2 — but it is a trade that gets easier to make every time it is made. Left ungoverned,
`known_gap` becomes where an inconvenient failure goes, and a corpus of documented gaps stays
green while asserting nothing.

So, enforced by `core/burrow-engines/tests/conformance.rs`:

| Rule | Where |
|---|---|
| An issue link, and a reason that is a sentence rather than a label | `every_known_gap_names_an_issue_and_a_milestone` |
| A **`milestone`** the gap must be closed by, from `M0`–`M6` | same test; an unrecognised name fails rather than sorting as zero |
| The milestone must still be **ahead of** `current_milestone` | same test |
| At most **`MAX_KNOWN_GAPS`** (2) entries in the whole corpus | `known_gaps_are_under_the_ceiling` |

`current_milestone` sits at the top of `expectations.json`. **Bumping it is the act that calls
in every outstanding gap**: each one whose milestone has been reached fails, and has to be
fixed, or re-targeted in a commit that says why the date moved. Deleting the case is not the
third option — that turns a documented defect into an undocumented one.

A declared milestone rather than a calendar date or a GitHub query, deliberately. A date gate
turns red on an idle branch for reasons that have nothing to do with the code. A query puts a
network call and a token inside a check that has to run offline and locally.

Both current entries target **M2**. Both are memory-enforcement gaps, and
[ADR 0015 §7](../../docs/adr/0015-web-worker-lifecycle.md) already defers that decision to a
pre-M2 gate — the same gate [#25](https://github.com/TensorGreed/burrow/issues/25) belongs to.
M2 is also where a file reaching 2.4 GB stops being merely wasteful, because redaction is what
runs on it.

### What `encrypted.pdf` does and does not cover

Its `/O` and `/U` strings are fixed arbitrary bytes, so authentication fails for every
password. That drives PDFium down its `FPDF_ERR_PASSWORD` path — which is the error
variant under test — without implementing RC4 and MD5 in the test support, because the
check is over the values in the dictionary, not over the streams.

It therefore covers *"encrypted, and the password did not work"*. It does **not** cover
*"encrypted, and the password did work"*: that needs a real encryptor, and qpdf arrives
in M1 PR 3. Recorded here so the gap is a known one rather than an assumed pass.

## Running the corpus costs about 500 MB

`objstm-bomb.pdf` inflates to 200 MiB and PDFium retains roughly that while the handle is open,
so the native suite peaks around **500 MB of address space**. On a CI runner that is nothing. In
a memory-capped container it matters, and the failure is unhelpful: PDFium's own out-of-memory
path calls `abort()`, which no `catch_unwind` intercepts, so the suite dies with `Aborted (core
dumped)`, exit 134, and **no indication of which case did it**. Reproduced at `ulimit -v 450000`.

That is inherent rather than incidental: these fixtures are cheap *because the checks they test
work*. If the pre-scan regresses, the suite itself becomes the 2.5 GB allocation — which is the
right way round for a regression to hurt.

## Changing a fixture

Fixtures are pinned by sha256 in `expectations.json`, so editing one fails
`every_fixture_matches_its_recorded_digest` rather than quietly changing what the suite
asserts. To change one deliberately:

1. Edit the generator in `core/burrow-engines/testsupport/minimal_pdf.rs`.
2. Re-run `cargo run -p burrow-engines --example make-conformance-fixtures`.
3. Review the diff to `expectations.json` — a changed *outcome* is a behaviour change and
   needs justifying; a changed digest alone is just a rebuild.

Expected outcomes in the generator are written by hand and never recorded from whatever
the engine currently returns. A corpus that records today's behaviour keeps passing
through the exact regression it exists to catch.
